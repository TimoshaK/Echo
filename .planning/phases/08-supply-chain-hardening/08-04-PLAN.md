2. **Prove the installed tree matches the lock exactly.** Run from the repository root so

   ```powershell
   A:\pip-tmp\venv-check\Scripts\python.exe -c "import importlib.metadata as m,pathlib,re
   t=pathlib.Path('requirements.txt').read_text('utf-8')

   ```

   Expected: `OK installed versions match the lock: 24`.

3. **Prove the app's imports resolve and this is the CPU build:**


   Expected: `imports ok 2.14.0 2.4.4 4.70.0`. The assertion that `torch.__version__` is exactly

Do **not** edit any lock file to make this pass. If a lock is wrong, that is a finding to report, not
something to paper over in a verification task.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Lock file → pip installer | The enforcement point; this plan is the only place it is exercised against a real install |
| PyTorch cu130 index → local environment | Second artifact source, exercised for real only in the checkpoint |
| Audit tool → advisory service | `pip-audit` queries external advisory data; its output is advisory, not authoritative |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-05 | Tampering | A lock that parses but cannot actually install (wrong hash, missing wheel, unsatisfiable pin) | mitigate | Task 1 installs the CPU lock in a clean venv under `--require-hashes` and asserts the installed versions match the lock exactly; Task 3 does the same for the CUDA lock on real hardware |
| T-08-21 | Tampering | Verification task silently "fixing" a broken lock to make itself pass | mitigate | Explicitly prohibited in Tasks 1 and 2; a lock defect must be reported as a finding, not patched inside a verification plan |
| T-08-22 | Elevation of Privilege | Unhashed PEP 517 build dependencies executing during the `openai-whisper` sdist build | accept | Structural: `openai-whisper` publishes no wheel, so a build is unavoidable; `--require-hashes` covers the sdist itself but not its build backend. Residual risk is documented in the README's install section and recorded here |
| T-08-23 | Information Disclosure | A verification step reading or printing `app_config.json` (the operator's API key) | mitigate | Every probe in this plan reads only lock files and docs; `app_config.json` is never opened |
| T-08-24 | Denial of Service | The ~2.8 GB CUDA download exhausting disk or bandwidth unmonitored | mitigate | Isolated in a blocking human-verify checkpoint rather than an automated task, so the operator controls when it runs and can delete the scratch venv afterwards |
| T-08-25 | Tampering | A vulnerable transitive dependency shipping unnoticed | mitigate | `pip-audit` is run against both locks; advisories are recorded verbatim so they cannot be silently dropped |
</threat_model>
